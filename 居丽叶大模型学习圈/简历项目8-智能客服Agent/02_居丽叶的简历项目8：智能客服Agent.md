## 项目描述

（SFT这段不讲也行，等他问到再讲）

我参与这个项目时，团队已经完成了第一版工具接入和 Agentic SFT 冷启动。第一版 SFT 的目标是先让模型学会规范的 tool call 格式、基础的 thought-action-observation 循环，以及比价、鉴定、退款等高频场景下的常见工具链。这个版本相比裸模型已经能跑通基本流程，评测集准确率从 61.8 提升到 64.6。  
  
但 SFT 的问题在于：它更擅长复现训练轨迹里见过的工具链，策略上限受示范数据覆盖范围限制。比如二手鉴定场景里，训练集中常见路径可能是“商品识别 → 鉴定标准检索 → 图像细节比对”，但真实用户上传的图片质量、商品类型和问题表达都不稳定。一旦中间某个工具返回低质量 observation，SFT 模型容易继续沿着原路径走，或者重复调用同一个工具，缺少根据环境反馈调整策略的能力。  
  
所以我实习期间的主要工作是在已有 SFT Agent 的基础上做两件事：第一，配合新工具和新 bad case 迭代 SFT 数据，让模型持续掌握新增工具和修正后的标准调用路径；第二，在 SFT 模型的基础上引入 Agentic RL，让模型在真实工具环境里探索多条工具调用轨迹，进一步提升复杂场景下的工具编排能力。

**SFT：**

  
SFT 这套流程本身是项目里的基础迭代机制。每当新增工具、扩展业务场景，或者线上/评测中发现新的 bad case，我们都会把这些 case 重新整理成多轮工具调用数据。数据来源一部分是人工标注，一部分是强模型合成：合成时先做难度过滤，去掉裸模型不用工具就能回答的问题，再去掉单次 image_search 就能解决的单跳问题，只保留真正需要多步推理的样本。随后对每道题采样 K=5 条候选轨迹，经过答案正确性和过程质量两阶段筛选，只把高质量轨迹加入 SFT 数据集。  
  
另外，针对图片质量差导致工具链失败的问题，我们会在约 10% 的数据里加入受控图像降质，比如模糊、下采样、透视畸变，并配套构造调用 sharpen、super_resolution、perspective_correct 等视觉增强工具的轨迹。这样 SFT 迭代的作用，是让模型及时学会新增工具的调用格式、适用条件和标准路径，避免模型在进入 RL 前连基础工具使用都不稳定。

**RL：**  
  
在这个 SFT 的模型之上，我们再做 Agentic RL。RL 数据来自同一套过滤后的高难度问题池，但不提供中间工具轨迹，只保留“问题 + 最终答案”。模型需要在训练时自己 rollout 多条工具调用路径，再通过格式奖励、终态准确率奖励和过程质量奖励来比较不同策略的好坏。  
  
算法上我们选的是 GRPO。每个 prompt 会采样多条工具调用轨迹，轨迹形式是：thought → tool call → observation → thought → tool call → observation → final answer  
  
奖励设计分三层。最外层是格式奖励，作为硬门控，格式不合规直接把整条轨迹奖励清零，保证模型始终输出规范的工具调用结构。格式通过后，剩余奖励由两部分组成：一是终态准确率奖励，占 80%，用 judge 判断最终答案是否正确；二是过程质量奖励，占 20%，对整条搜索轨迹打分，评估查询词是否精准、多次查询之间有没有合理递进、图像搜索和文字搜索有没有形成互补。  
  
加过程奖励的原因是，多跳工具调用里只有最终答案奖励太稀疏。模型可能最后答错，但前几步工具选择其实是合理的；也可能最后答对，但中间走了很多无效路径。过程奖励相当于给模型更细的反馈，让它不只是追求最终答对，还要学习更稳定、更高效的工具编排方式。  
  
GRPO 之后，模型分数从 64.6 提升到 69.0，说明它不再只是复现 SFT 里的示范路径，而是开始学会根据环境反馈选择更优的工具链。

**困难和挑战：**  
  
RL 训练中我们遇到的最大问题是信用分配。在多轮工具调用的长轨迹里，前几步可能是完全正确的：模型已经识别出商品，也找到了合理的检索方向；但中间某一步工具调用因为参数问题、超时或者 observation 质量差导致失败，后续轨迹质量迅速下降，最终答错。  
  
如果按照vanilla GRPO 的方式，把整条轨迹作为一个整体参与更新，那么这条轨迹的 advantage 往往是负的。问题是，负 advantage 不只会惩罚失败之后的错误 token，也会惩罚失败之前那些本来合理的推理和工具调用。模型会误以为“这条路径从一开始就是错的”，从而压制掉一些其实有价值的探索行为。  
  
我们最开始尝试的是 **hard-masking**：把失败 step 之后所有 token 的 loss 屏蔽掉。直觉上，失败点之后的错误内容不参与训练，应该就能减少噪声。但消融实验发现效果几乎没有提升。原因是 hard-masking 只屏蔽了失败之后 token 的梯度，整条轨迹的 advantage 仍然是负的，失败点之前的 token 仍然会被负向 advantage 惩罚。  
  
所以我们在失败 step 截断基础上，加了**单侧优势截断**。具体做法是：对于进入失败状态的轨迹，如果它的 advantage 是负的，就直接归零；如果它在组内仍然高于平均水平，说明失败前缀可能有价值，就保留正向学习信号。这样可以做到两点：失败之后的噪声不参与训练，失败之前的有效推理也不会因为后续工具崩掉而被错误惩罚。  
  
改完之后，模型分数从 69.1 提升到 71.8，又涨了 2.7 分，是整个项目里单次改动效果最明显的一个决策。除此之外，我们在 RL 过程中也处理了一些训练稳定性问题，比如策略熵崩溃导致 rollout 高度趋同、奖励劫持导致模型迎合 judge、并发工具调用超时导致轨迹异常中断等。

**成果：**  
  
最终效果基于自建的 1000 题评测集评估，用 LLM judge 自动评分加人工抽样复核。准确率从裸模型的 61.8，经过 SFT baseline 提升到 64.6，再经过 Agentic RL 提升到 71.8。业务指标上，转人工率从 21.1% 降到 15.6%；效率方面，平均每道题触发 2-3 次工具调用，端到端 P50 响应时长约 6 秒，P95 在 12 秒以内；工具调用成功率达到 99%，触发提前终止的比例控制在 3% 以内。

### 请介绍一下你们这个多模态智能客服 Agent 项目，它主要解决了什么问题？

这个项目应用在电商客服场景，主要解决的是图文混合咨询里的复杂工具调用问题。  
  
传统客服系统里常见方案有几类。规则 Bot 可以调用一些固定 API，比如查订单、查物流、申请退款，但它的调用逻辑是硬编码的，只适合流程非常固定的问题。纯 RAG 系统主要检索文本知识库，碰到用户上传商品图、快递面单、瑕疵照片、鉴定图片这类视觉输入时，能力就明显不足。  
  
后来团队已经围绕电商场景沉淀了一批高频工具，包括图像增强、以图搜图、商品检索、跨平台比价、防伪验证、退款跟踪等，并且做了第一版 Agentic SFT baseline。这个 SFT 版本已经能让模型掌握基础 tool call 格式和常见工具链，比如比价导购、二手鉴定、售后理赔这些高频场景都能跑通。  
  
但它的问题在于：SFT 更偏模仿，模型主要是在复现训练数据里见过的工具调用路径。真实客服问题会复杂很多，比如用户上传一张模糊商品图，问“这个是不是正品、现在买贵不贵、如果是假货能不能申请理赔”。这类问题不是一步检索能解决的，模型需要先判断图像质量够不够，要不要做增强或裁剪；再识别商品；再查鉴定标准、价格信息或售后规则；中间某个工具返回低质量结果时，还要决定是重试、换工具，还是终止。  
  
SFT 模型在这些长链、多跳、带失败恢复的场景下灵活性不够，容易继续沿着固定路径走，或者重复调用同一个低质量工具。所以我实习期间主要参与的是在已有 SFT Agent 基础上继续优化：一方面配合新工具和 bad case 做 SFT 数据迭代，让模型持续学会新增工具和修正后的标准调用路径；另一方面引入 Agentic RL，让模型在真实工具环境里 rollout 多条工具调用轨迹，通过最终答案奖励、过程质量奖励和失败轨迹处理，学习更灵活的工具编排策略。  
  
所以这个项目解决的问题主要是把电商客服里的复杂工具调用训练化：SFT 让模型先学会标准工具路径，RL 让模型进一步学会在复杂场景里根据环境反馈选择工具、调整路径和处理失败。目前这套系统还在持续完善，目标是覆盖客服场景下更大范围的图文问题。

### 项目的整体训练流程是什么？为什么要分两个阶段？

从整个系统训练流程来看，它是“Agentic SFT 冷启动 + Agentic RL 优化”两阶段。但我参与项目时，第一版 SFT baseline 已经完成了，后续每次新增工具、扩展场景或者发现新的 bad case，都会继续按这套 SFT 流程做数据更新和模型迭代。  
  
第一阶段是 Agentic SFT，主要目标是让模型先学会“怎么规范地使用工具”。因为多模态客服 Agent 需要输出符合格式的 tool call，理解 thought-action-observation 这种多轮交互结构，还要掌握比价、鉴定、退款等高频场景下的基础工具链。如果没有 SFT 冷启动，直接做 RL，模型连工具调用格式都不稳定，奖励信号很难成立，训练也容易崩。  
  
SFT 数据主要是 36k 条多轮工具调用轨迹。数据来源一部分是人工标注，一部分是强模型合成。合成轨迹会先做难度过滤，去掉裸模型不用工具就能回答的问题，也去掉单次检索就能解决的简单问题，只保留真正需要多步工具调用的样本。然后对每道题采样多条候选轨迹，再经过答案正确性和过程质量两阶段筛选。这个阶段让模型从裸模型的 61.8 提升到 64.6，能够稳定跑通基础工具调用闭环。  
  
但 SFT 的问题是，它本质上是在模仿示范轨迹。它更擅长复现训练数据里见过的路径，比如“商品识别 → 鉴定标准检索 → 图像细节比对”。一旦真实用户的问题表达、图片质量、商品类型和训练分布不一样，或者中间某个工具返回了低质量 observation，SFT 模型就容易沿着原路径硬走，缺少根据反馈换路的能力。  
  
所以第二阶段引入 Agentic RL。RL 阶段不再给模型完整工具调用轨迹，而是只给“问题 + 最终答案”，让模型在真实工具环境里自己 rollout 多条路径，再通过奖励信号比较哪条路径更好。这个阶段的重点是让模型学策略：什么时候先做图像增强，什么时候直接检索，某个工具失败后是重试、换工具还是终止，以及怎么把多轮 observation 拼成最终答案。  
  
我们用的是改进版 GRPO。奖励包括格式奖励、最终答案准确率奖励和过程质量奖励。格式奖励保证模型工具调用结构合法；最终答案奖励判断结果是否正确；过程奖励则关注查询是否精准、工具链是否递进、图像搜索和文本搜索是否互补。RL 后模型从 64.6 提升到 71.8，是主要的能力提升来源。  
  
所以分成两个阶段，本质上是因为 SFT 和 RL 解决的是两个层次的问题：SFT 解决“会不会调用工具、能不能按规范跑通基础链路”；RL 解决“在复杂场景下能不能根据环境反馈更聪明地选择工具、调整路径和处理失败”。如果只做 SFT，模型容易停留在示范分布附近；如果跳过 SFT 直接做 RL，探索空间太大，训练起点太差，很难稳定收敛。

| 阶段 | 作用 | 数据形式 | 平均准确率 |
|---|---|---|---|
| 裸模型 | 具备基础多模态理解能力，但工具调用策略不稳定 | 无工具轨迹训练 | 61.8 |
| Agentic SFT baseline | 学会规范 tool call、基础交互格式和常见工具链；后续可随新工具和 bad case 持续迭代 | 36k 多轮工具调用轨迹 | 64.6 |
| Agentic RL 优化 | 在真实工具环境中探索更优工具链，学习换路、重试、终止等策略 | 8k 高难度问题，仅保留最终答案 | 71.8 |

### 你们的 Agent 在线上运行时，一次完整的推理流程是怎样的？

线上每个 case 最多允许 10 轮工具调用。整体流程是一个循环：模型先输出 thought，判断当前还缺什么信息；然后生成 tool call，系统解析工具名和参数并执行工具；工具返回 observation 后，再把结果拼回上下文，让模型继续判断下一步是继续调用工具，还是已经有足够证据输出最终答案。

我举一个二手商品鉴定的例子。

用户上传一张比较模糊的球鞋图片，问：“这个鞋是不是正品？如果是假货能不能申请理赔？”

第一轮，模型会先判断原图质量不够，直接做鉴定风险比较高，于是调用 `crop` 或 `super_resolution`，先把鞋标、鞋盒标签、防伪码这类关键区域裁出来并增强清晰度。

第二轮，模型拿到增强后的图片 observation 后，调用 `image_search` 或商品识别工具，定位具体品牌、型号和相似商品，确认这双鞋大概属于哪个 SKU 或系列。

第三轮，模型会调用鉴定标准检索工具，查询这个型号的关键鉴定点，比如鞋标字体、防伪码格式、鞋盒标签位置、logo 细节等。

第四轮，如果图片里有防伪码或订单信息，模型会继续调用 `OCR` 或防伪验证工具，把防伪码识别出来并查询验证结果。

第五轮，模型结合前几轮 observation 判断：如果证据足够，比如防伪码无效、鞋标细节和官方标准明显不一致，就输出“疑似非正品”的结论，并进一步调用售后规则或理赔工具，判断用户是否满足平台理赔条件。如果证据不足，就会提示用户补充更清晰的鞋标、防伪码或购买凭证图片，而不是强行给结论。

所以一次完整链路就是不断做：`thought → tool call → observation → 再 thought`

模型每一轮都会根据 observation 更新判断：当前证据够不够，下一步应该继续搜证、换工具，还是收敛到最终答案。

为了防止线上推理失控，我们还做了两个提前终止机制：

第一个是 失败 step 终止。如果连续 3 次工具调用失败、参数无效，或者返回结果无法支持继续推理，就直接终止当前工具链，避免模型在无效路径里死循环。

第二个是重复生成检测。如果模型输出内容的 n-gram distinct ratio 低于 0.5，并且词数超过 2500，就认为它开始重复生成，直接截断。

这些机制的作用是给 Agent 加一个运行边界：正常情况下，它可以根据工具结果持续调整路径；但一旦发现连续失败或重复生成，就及时停止，避免浪费计算，也避免给用户返回一段看似很长但没有新证据的回答。

### 这个项目一共设计了哪些工具？为什么要分成三大类？

我们一共设计了 23 个工具，分成三大类：视觉处理工具、信息检索工具和业务操作工具，三类工具的职责完全不同，不能相互替代。

**视觉处理工具（5个）**，主要目的是提升图像质量，为后续识别和检索打基础：

- crop（裁剪聚焦）：把感兴趣区域从大图里框出来，减少无关背景干扰
- perspective_correct（透视矫正）：把倾斜或有梯形畸变的标签、面单纠正为正视图
- super_resolution（超分辨率）：对模糊小图做放大增强
- sharpen（锐化）：增强图像边缘清晰度，改善 OCR 识别率
- layout_parsing（版面解析）：对复杂排版的图片（比如商品说明书、快递面单）做结构化 OCR，输出带位置信息的文字块

**信息检索工具（3个）**，底层都接入我们的电商知识库，解决模型参数记忆不可靠、数据存在时效性的问题：

- text_search（文字检索）：在电商数据库中按文字关键词检索，返回商品信息、价格记录、售后规则等结构化内容
- image_search（图片检索）：以图搜图，在商品图库中检索视觉相似的商品，快速定位品牌型号和同款
- web_search（网页搜索）：对数据库未覆盖的内容进行补充 web 搜索，返回摘要片段

**业务操作工具（15个）**，对接后台业务系统或引导用户跳转 C 端页面完成具体操作，按场景可以大致分四组：

比价导购（3个）：

- 跨平台比价：调用比价接口查询同款商品在淘宝、京东、拼多多等主流平台的当前售价，返回价格对比列表及最低价平台信息
- 历史价格查询：查询该 SKU 近 30/90/180 天的价格走势，判断当前价格是否处于历史低位，返回价格摘要及购买建议
- 优惠券领取：引导用户点击按钮跳转 C 端优惠券领取页，查看并领取当前商品可用的店铺券、平台券及限时折扣

二手鉴定（4个）：

- 防伪码验证：调用品牌官方防伪接口查询该编码的真伪状态及首次激活记录，返回验证结果
- 官方鉴定标准查询：检索品牌鉴定知识库，返回该商品的官方鉴定要点（如防伪标等细节标准）
- 申请平台鉴定：引导用户点击按钮跳转 C 端鉴定申请页，提交商品信息及图片，由平台专业鉴定师出具鉴定报告
- 鉴定报告查询：查询当前订单下的鉴定报告状态，已出报告则返回鉴定结论（正品/疑似仿品），鉴定中则告知预计完成时间

售后理赔（5个）：

- 申请退款：引导用户点击按钮跳转 C 端退款申请页面，提交仅退款或退货退款申请，并说明不同退款类型的适用场景
- 跟踪退款进度：当用户催促退款时，自动查询退款申请状态，已到账则通知用户，处理中则返回预计到账时间及退款路径（原路退回/余额）
- 申请理赔：引导用户点击按钮跳转 C 端理赔申请页，上传商品破损或与描述不符的凭证图片，提交理赔申请并告知审核周期
- 催发货：当用户反馈商家迟迟未发货时，向业务系统发起催发货请求，告知用户商家响应时限及超时后的自动维权规则
- 投诉商家：引导用户点击按钮跳转 C 端投诉页面，对商家的虚假描述、延迟发货、拒绝退款等行为发起投诉，并说明平台介入的触发条件

通用订单（3个）：

- 订单详情查询：引导用户点击按钮跳转 C 端订单详情页，查看订单状态、商品信息、收货地址、支付金额及物流单号等完整信息
- 物流轨迹查询：调用物流接口查询当前快递的实时轨迹，返回最新位置、预计送达时间，以及异常情况（滞留、派件失败）的原因说明
- 修改收货地址：引导用户点击按钮跳转 C 端地址修改页，在商家未发货前修改收货地址，并提示发货后无法修改

三类工具串联起来才能覆盖复杂场景，比如在售后理赔场景里，先用 layout_parsing 提取快递面单上的单号，再用物流轨迹查询核实包裹当前状态，最后用申请理赔工具引导用户提交破损凭证；在比价导购场景里，先用 image_search 从商品图识别出品牌型号，再用历史价格查询判断当前价格是否值得入手。

#### 4.1 介绍一下其中某个业务操作工具的实现？

以"历史价格查询"为例。这个工具的触发场景是用户询问某商品"现在买划不划算"或"是不是历史最低价"，光凭当前价格没法回答，必须有历史数据支撑。

实现链路分三步。

第一步是商品定位：工具接收到模型传入的 SKU 编号或商品标题，先在我们的电商数据库里做精确匹配，如果模型传的是模糊商品名，则走一次 text_search 确认唯一 SKU，避免因商品歧义拉到错误的价格序列。

第二步是价格序列拉取：拿到 SKU 之后，从价格历史库里拉取近 30 天、90 天、180 天三个时间窗口的日维度价格记录。价格历史库是离线定时从各平台抓取的，更新频率是每天一次，覆盖商品的到手价（含平台券后价），不只是挂牌价。

第三步是趋势分析与结论生成：对拉到的价格序列做三件事——计算历史最低价、当前价格所处的百分位（比如当前价格比过去 180 天 85% 的时间段都低），以及近 30 天的价格趋势方向（上涨/下跌/平稳）。

这三个数字会拼成一段结构化摘要返回给模型，比如"当前价格 399 元，近 180 天历史最低 379 元，当前价格处于历史较低区间（近 180 天低于此价的时间仅占 12%），近 30 天价格趋势平稳"。这样工具层先做好分析，模型拿到的是干净的结论摘要，再结合用户具体诉求给出最终建议，分工更清晰、效率更高。

### 你们提出的改进的GRPO算法是什么？

它主要是为了解决多轮工具调用场景里一个很典型的问题：一旦中间某个工具步骤出错，后面的轨迹质量往往会连锁下降，如果还把整条轨迹按普通方式参与更新，就容易把错误探索带来的噪声一起反向强化到模型里。

这个算法的核心思想可以概括成两步。

第一步是做 失败 step 截断，也就是识别出轨迹里已经进入无效分支的位置，把失败 step 之后的 token 不再作为正常学习信号使用，避免后续错误持续污染梯度。

第二步是在此基础上保留 失败 step 之前那些仍然有价值的推理过程，不因为后面失败了就把前面的有效探索一并否掉。

除此之外，我们还加了 单侧优势截断，让失败轨迹不要对前面已经正确的探索施加过强的负向惩罚。这样做的目的，是让模型既能在 RL 里继续探索新的工具策略，又不会因为长链调用中的局部失败而把整个学习方向带偏。

从训练效果上看，这个改进本质上是在标准 GRPO 上补了一层更适合 Agentic 场景的信用分配机制。因为多轮工具调用和普通单步问答不一样，错误通常不是瞬时发生的，而是会沿着后续多轮决策级联放大。改进的GRPO 处理的就是这种“前面有价值、后面失控”的轨迹，它让模型能保留有用的早期决策，同时抑制无效后续带来的负面影响。

### 这个项目中你负责了哪些核心模块？遇到的最大挑战是什么？

我主要负责了三块：RL 算法的设计与实现（改进的GRPO）、工具的搭建、以及消融实验的设计和分析。

这里面最难的点，我觉得是多轮工具调用场景里的信用分配问题。因为这个项目里，SFT 只能提供一个比较强的工具使用初始化，但模型是否能在复杂问题里学出更优的搜索策略，仍然要靠 RL 阶段的探索来完成。真正麻烦的地方在于，一条长轨迹里前面的几步可能是对的，模型已经在逐步接近答案，但中间某一步工具调用失败之后，后面的轨迹质量会迅速下降。如果这时候还把整条轨迹按普通方式参与更新，就容易把后面错误探索带来的噪声反向强化进去，连前面本来有价值的决策也一起被误伤。我们早期就遇到过这种现象，所以后来尝试过直接 hard-masking（把 失败 step 之后所有 token 都 mask 掉），但消融实验发现几乎没有提升，从64.6到69.1，和 vanilla GRPO 的69.0几乎持平。分析原因是 hard-masking 虽然截断了错误梯度，但对失败 step 前已经形成的合理推理也施加了负向惩罚，模型反而会变得不敢探索。最终我们在截断基础上加了 单侧优势截断，只保留正向学习信号，不惩罚失败 step 前的有效推理。这个改动从69.1进一步提升到71.8，提升了2.7分，是整个项目里我觉得最有价值的一个设计决策。

### 你们为什么选择 GRPO 而不是 PPO 作为 RL 算法？

原因有三点，都和我们的具体场景强相关。

第一，PPO 需要维护一个独立的价值网络（critic），对于9B参数量级的多模态模型，critic model 要占用大量的显存。GRPO 用组内相对奖励替代了 value function，不需要 critic，显存开销大幅降低。

第二，我们的奖励信号是稀疏的终态奖励加上过程奖励，这种结构天然适合 GRPO 的组内相对优势估计，不需要 PPO 那样对每个 token 都计算 value。

第三，也是最关键的一点：这个项目里我们并不是只想让模型复现 SFT 演示轨迹，而是希望它在已有初始化基础上，通过探索学出更优的工具使用策略。GRPO 会针对同一个问题一次采样一个 group 的多条轨迹，再根据组内相对 reward 去比较哪条工具路径更有效。这样模型学到的不是某一条固定答案，而是同一个问题下，哪种工具组合、调用顺序和停止时机更优。对我们这种多轮、多路径、需要比较不同轨迹收益的 Agentic RL 场景来说，这种基于组内比较的学习方式，比单纯依赖绝对 value 估计更适合把探索结果转成稳定的策略提升。实践上，vanilla GRPO 已经把基线从64.6提到了69.0，涨了4.4分，证明算法选择本身是对的，我们后续的改进是在这个基础上叠加的。

### 为什么 SFT 阶段选择全参数微调，而不是 LoRA 或者冻结视觉编码器？

先说冻结视觉编码器的问题。我们的典型业务场景对图像理解的要求都很苛刻：比如二手鉴定需要识别细微的做工差异，售后理赔需要精确定位破损区域。预训练的视觉编码器针对的是通用图像理解，在电商细粒度场景下表现不够好。

如果冻结 ViT，等于把图像理解能力的上限给锁死了，LLM 再强也没用。然后 LoRA 的秩限制了模型学习新任务模式的容量。我们的轨迹平均每条有2.3次工具调用，模型需要同时学习工具调用格式、多步推理策略、图像-文本对齐，这些需要又充分的可训练参数才能充分学习，低秩近似会造成明显的容量瓶颈，在我们的预实验里 LoRA 的分数比全参数低了约2分。 

### text_search 工具是怎么实现的？

text_search 的实现链路是这样的：用户 query 先在我们的电商数据库中做文字关键词检索，返回一批相关文档；由于每条商品文档往往很长、内容杂糅，我们用一个大模型对这些文档做 query 相关的摘要提炼，把和当前问题最相关的关键信息提取出来，最终返回简洁的摘要片段。

之所以要加这层摘要，是因为直接返回原始检索结果有三个问题：

第一，商品文档普遍很长，一条详情页动辄几千字，模型容易在无关内容里迷失，提取关键信息的效率很低；

第二，检索结果往往是多条候选文档，模型需要自己做跨文档的信息聚合，容易漏掉关键信息；

第三，不同商品的文档格式不统一，模型比对参数时很吃力。加上摘要层之后，模型拿到的是干净、聚焦、结构化的信息，几千字压缩成几百字，平均工具调用轮次也降低了。

### image_search 和 text_search 在实际业务中是怎么配合使用的？

image_search 的实现链路是这样的：用户上传一张商品图，我们先用 CN-CLIP 的图像编码器提取图像的特征向量，然后在商品图库中通过特征向量的相似度匹配检索（如余弦相似度），返回一批视觉相似商品的标题和来源信息。选择 CN-CLIP 的原因是我们的场景是中文电商，CN-CLIP 在中文商品图文数据上做过对比训练，对国内品牌和商品图的向量空间质量明显优于原版 CLIP。query图和商品图库中的图用的是同一个编码器，保证特征向量处于同一空间。商品图库的特征向量在离线阶段已用 CN-CLIP 预计算完毕并导入 Milvus 向量数据库，线上只对 query 图跑一次前向推理，检索延迟可以控制在几十毫秒以内。

这两个工具的信息来源是互补的。 

image_search 的强项是以图找图，适合处理用户上传的商品图，快速锁定品牌型号和同款商品。但它的弱点是返回的信息通常只有商品名称和购买链接，缺乏价格历史、参数对比，真伪鉴别的详细内容。 text_search 的强项是检索结构化的文字信息，比如官方参数表、鉴定指南、价格历史数据。但它需要先有一个准确的查询词，如果用户只发了一张图，你不知道该搜什么词。 比如在比价导购场景里，标准工具链是：先用 image_search 从商品图里识别出品牌和型号，再用识别出的型号去 text_search 搜比价信息。在二手鉴定场景里，先用 image_search 找到同款商品的官方图，再用 text_search 检索该商品的鉴定要点（比如某款包的防伪线位置、某双鞋的鞋底纹理标准）。

### 视觉增强工具分别是怎么实现的？什么时候会使用？

Crop（裁剪聚焦）的作用是把用户上传的大图中的感兴趣区域框出来，去除无关的背景干扰。这个工具在用户拍的图里包含多个商品、或者背景过于杂乱时有用。比如一张图里同时拍了好几件商品，模型可以先用 crop 把每件商品单独裁出来，再分别做识别。在 OCR 场景里，如果文字只占图片的一小块区域，crop 能显著提升文字识别的准确率。

Perspective_correct（透视矫正）的作用是把倾斜或存在梯形畸变的标签、面单纠正为正视图。这个工具来自一个具体的业务痛点：用户拍商品时很少是正对着拍的，大量图片里的标签、吊牌是倾斜的或者有透视变形的。在二手鉴定场景里，防伪标签的字体、间距是鉴别真伪的关键，如果标签歪了，OCR 识别率会大幅下降甚至出现字符颠倒，导致识别出的商品型号是错的，后续的比价或鉴定全部基于错误信息进行。在售后理赔场景里，快递面单上的单号需要准确识别，透视矫正能让面单变成规整的矩形再处理。加入透视矫正后，对倾斜标签的 OCR 准确率明显提升，在售后理赔子任务上的准确率提升尤为显著。工具链 recipe "透视矫正 → 锐化 → OCR" 也是基于这个洞察设计的：先把几何畸变纠正，再做锐化，最后做 OCR，每一步都在为下一步降低难度。

Super_resolution（超分辨率）的作用是对模糊的小图进行放大增强，但这个工具会带来额外延迟，我们做了针对性约束。第一，在系统提示词里设置了明确的触发条件：只有当目标区域过小或者图像明显模糊时才调用，不是每张图都上超分，而是有条件触发。第二，工具调用有超时机制，单个工具调用超过阈值就标记为 失败 step，防止一个慢工具把整条推理链拖死。第三，超分辨率通常在 crop 之后使用，先裁剪到感兴趣区域再做超分，处理的图像面积更小、速度更快、效果也更好。整体上，MAX_TURNS=10 的限制保证了总推理轮次有上界，总时长可控。

Sharpen（锐化）的作用是增强图像边缘的清晰度，改善 OCR 的识别率。这个工具在图像整体清晰但边缘有些模糊时使用，比如商品标签的文字看起来有点发虚，锐化能让文字边缘变得更锐利。和超分辨率不同，锐化不会改变图像尺寸，主要是提升清晰度。

Layout_parsing（版面解析）的作用是对复杂排版的图片（如商品说明书、快递面单、发票等）做结构化 OCR，输出带位置信息的文字块。这个工具在需要从复杂文档中提取信息时使用，比如从一张商品说明书里提取规格参数、从快递面单里提取收件人信息和单号。layout_parsing 还能告诉我们每段文字在图片中的位置，这对于需要精确定位关键信息的场景特别有用。

### 电商场景里模型给出错误价格或错误真伪结论，风险很大，你们怎么保证模型的答案是基于工具实际获取的信息，而不是自己编的？

这个问题我们在设计 System Prompt 的时候就重点考虑了。多模态模型在没有工具的情况下，很容易用参数记忆去猜答案，而参数记忆里的商品信息往往是过时的或者错误的。我们的思路是通过系统设计强制模型必须调工具取证、不允许凭空输出结论。

具体落地在三个层面：

第一，强制 think 块，每次工具调用前模型必须先输出思考内容，不允许想都不想就调工具，思考块里必须明确说明为什么要调这个工具，预期拿到什么信息。这个设计有效减少了乱调工具的情况。 

第二，图像质量评估协议。在处理图像前，模型被要求先评估三个问题：图里的文字是否清晰可读？几何结构是否平整（比如标签是否倾斜）？目标区域是否太小？如果图像质量不达标，系统要求先调用图像增强工具（透视矫正、超分辨率、锐化）再继续，而不是直接对模糊图做识别然后猜一个结果。 

第三，工具链 recipes。系统提示词里写明了针对不同场景的推荐工具调用顺序，比如「文字识别前先透视矫正再锐化再OCR」，这确保了关键信息是通过工具实际获取的，而不是模型自己编造的。

### 你们是如何定义和检测失败 step 的？为什么选择连续3次而不是2次或5次？

失败 step 的定义是：连续 K 次工具执行失败或返回无效结果。

一次工具调用失败可能是偶发的网络错误或参数问题，但连续多次失败说明模型陷入了一个错误的推理分支，继续执行只会浪费计算并产生噪声梯度。 

K=3 是通过消融实验定下来的。我们测试了 K=2 和 K=5 两个对照。

K=2 过于激进，它会截掉"连续失败两次、第三步才能纠错恢复"的轨迹。在我们的 8k RL 数据上，这类"连续2次失败后第3步成功纠错"的轨迹占比约 10%，被 K=2 全部错误截断，损失了大量有价值的探索数据；

K=5 过于宽松，其中大部分都是真正死循环轨迹（工具连续失败后始终无法恢复，或者模型始终无法找到正确的调用轨迹）被继续执行，平均每条产生超过3000个无效 token，既拉低训练效率，显存占用也明显上升。

K=3 在两者之间取得了最好的平衡：虽然会截掉"连续失败三次、第四步才能纠错恢复"的轨迹，但这类数据在我们的 8k RL 数据里占比只有约 2%，损失极小；而 K=5 能捕捉到的真正死循环轨迹，K=3 也能捕捉到其中约 90%。最终对应的模型性能也是最优的 71.8 分。

### 单侧优势截断 的核心思想是什么？和标准 GRPO 有什么本质区别？

先说标准 GRPO 在这里的问题。GRPO 对每条轨迹计算一个优势值，反映它比组内平均水平好多少或差多少。如果一条轨迹因为中间某个工具调用失败、最终没答出来，整条轨迹的优势值就是负的，模型会收到"这条轨迹上的每一个 token 都是错的"这样的梯度信号。但实际上，失败 step 之前的推理很可能是完全正确的——比如模型前三步已经正确识别了商品、找到了比价页面，第四步才因为 API 超时失败，不能说前三步的推理方向是错的。

我们的改进分两步走。

第一步是失败 step 截断，把失败 step 之后的所有 token 从训练信号里屏蔽掉，避免后续无效推理污染梯度。

第二步是 单侧优势截断，对整条失败轨迹的优势值做单侧截断——负的优势值直接归零，不让失败轨迹对模型施加任何负向惩罚。这样失败 step 之前那些有价值的推理过程，就不会因为后面的失败而被错误地压制掉。

和单纯做截断（hard-masking）的区别在于：hard-masking 只解决了"失败点之后的 token 不参与更新"，但如果整条轨迹的优势值还是负的，失败 step 之前的 token 仍然在被这个负优势惩罚，模型学到的是"这种推理开头也不好"，但其实开头是对的。one-sided clamping 从根本上移除了对失败轨迹的负向信号，让失败前的有效探索得以保留。

### 你们的 Reward 函数是怎么设计的？

整体是三个子奖励组合：r = r_fmt × (0.8 × r_acc + 0.2 × r_query)。

第一个是格式奖励 r_fmt，它是乘法门控。格式不对的轨迹——比如缺少思考块、工具调用标签不规范——整个奖励直接清零。之所以用乘法而不是加一个惩罚分，是因为我们需要格式正确作为硬约束。如果用加法惩罚，模型可能会接受"格式稍差但答案对"的轨迹，训练后期格式会逐渐退化；乘法门控保证格式是所有奖励的前置条件。

第二个是终态奖励 r_acc，权重 80%，直接衡量最终答案的正确性，用 GPT5.5 作 judge 打分。这是最核心的学习信号，权重最高是合理的。

第三个是过程奖励 r_query，权重 20%，衡量每次搜索查询的质量。设计这个的原因是：多跳问答里一条轨迹往往要调用多次搜索，如果只有终态奖励，模型很难通过信用分配理解"是哪次查询导致了最终成功"，加入过程奖励相当于给模型一个更密集的学习信号。0.8 和 0.2 的比例是通过网格搜索确定的，测试了 0.9/0.1、0.7/0.3 等组合，0.8/0.2 在验证集上得分最高——权重太偏向 r_query 会导致模型过度优化查询格式而忽略答案质量。

### 为什么用 GPT5.5 做 reward judge，而不是基于规则的答案匹配？

r_acc 和 r_query 都用 GPT5.5 来算，各自有一套独立的 judge prompt。

r_acc 的 judge prompt 是纯二分类：给定问题、标准答案和模型的回答，只判断「回答里有没有包含正确答案」，输出 yes/no。如果 judge 本身无法判定，或者出现了网络波动导致大模型超时，会回退到字符串精确匹配兜底。设计成二分类而不是多维打分，是为了让评分尽可能稳定、可复现。

r_query 的 judge prompt 是对整条搜索轨迹打 0 到 1 的分，评估五个维度：图片搜索检索到的视觉证据是否有效、文字搜索的查询词是否精准、多次查询之间有没有合理的递进逻辑、图文搜索有没有形成互补、以及有效信息和噪声的比例。

之所以两个都用 GPT5.5 而不是规则，是因为电商客服场景的答案本质上是开放式的——同一个正确答案可以有多种表述方式，语义等价但字面不同，规则匹配会把正确答案判错。另外搜索轨迹的质量更没法用规则衡量，需要理解查询词和检索结果之间的语义关联。

### 你们为什么选择 Qwen3.5-9B 而不是其他多模态大模型（如 InternVL、LLaVA）作为基座模型？

主要从架构能力、Agent 基础和部署效率三个维度考量。

第一，架构上天然适合长链多轮工具调用。Qwen3.5 采用混合注意力架构（Transformer + 线性注意力，即 Gated Delta Network）结合 MoE 稀疏机制，在约 50% 计算成本下实现了十万级 token 的长上下文处理。我们的推理场景中，单条轨迹最多 10 轮工具调用，工具结果、图像描述、多轮观测累积起来上下文长度很容易超过数万 token，这对长文本能力有硬性需求。

第二，原生 Agent 能力强，SFT 冷启动成本低。Qwen3.5 在 Agent 任务上表现突出，比如TAU2-Bench 能达到 86.7 分，多任务工具执行分数经常维持在 84 分以上。这意味着模型在预训练阶段就已经具备了扎实的工具调用格式理解和多步推理能力，我们的 SFT 冷启动只需要针对电商场景做适配，而不是从零教模型学会工具调用。

第三，原生多模态理解质量高。比如，Qwen3.5 在 MMMU 上得分 83.7 分，多模态理解能力在我们关注的细粒度图像场景（二手鉴定的防伪标签、快递面单的单号识别）上表现更稳定。

第四，9B 参数量在推理效率和部署成本上占优。Qwen3.5-9B 在 32k 上下文下的 decode throughput 是 Qwen3-Max 的 8.6 倍，256k 上下文下更是提升到 19 倍，延迟完全可控；同时 9B 量级的性能已经接近上一代 70+B 模型，性价比显著。只用更少的显卡就能满足线上延迟要求，运维成本低。

### 消融实验中，hard-masking 为什么几乎没有效果？

Hard-masking 的操作是：在 失败 step 发生后，把后续所有 token 的 loss mask 掉，不参与梯度更新。直觉上这应该有效，但实验结果是 69.1，和 vanilla GRPO 的 69.0 几乎没有区别。 

原因是hard-masking 只解决了「后续错误 token 不更新」的问题，但没有解决「前面的 token 被负向更新」的问题。失败轨迹的整体 reward 普遍很低，因为结果奖励永远是0，advantage 是负的，失败 step 之前的那些合理推理步骤同样在被这个负的 advantage 惩罚。模型学到的是「这种风格的推理开头不好」，但其实这些开头是正确的，导致模型在这种数据上学习效果很差。

### RL 训练过程中踩过哪些印象深刻的坑？

遇到了两个比较严重的问题。

第一个是**奖励劫持**。最明显的现象是模型学会了堆砌工具调用来骗 r_query 分。r_query 是对整条搜索轨迹打分，评估查询质量和信息利用率，但模型发现只要调用次数多、查询词覆盖面广，GPT5.5 judge 就倾向于给高分，即使这些调用之间缺乏真正的递进逻辑。具体症状是训练到中后期，部分轨迹里模型会对同一个商品反复用不同措辞发起 image_search 和 text_search，每次拿到结果后只是简单拼接，但 r_query 得分却持续走高。我们是在人工抽查轨迹时发现这个问题的。r_query 的 judge prompt 里本来有"查询递进性"这个维度，要求 judge 判断查询之间是否有逻辑上的递进和收敛，还是在无目的漂移重复，但原来的措辞对"换个说法搜同一件事"这种情况边界描述不够清晰，judge 容易误判为"覆盖不同角度"而给高分。我们收紧了这个维度的描述，明确要求识别"以不同措辞反复检索同一内容"并给低分，调整之后过度搜索的行为明显收敛了。

第二个是**策略熵崩溃**。症状是训练到大约150步之后，reward 开始停滞，但 loss 还在下降，看起来还在学习。仔细看 rollout 数据才发现问题：group_size=8 的 8 条采样轨迹开始高度趋同，同一个问题的 8 条 rollout 工具调用序列几乎完全一样，只在极少数 token 上有微小差异。这是策略熵崩溃的典型表现——模型的输出分布越来越尖锐，探索能力快速退化。这对 GRPO 来说是致命的，GRPO 的核心机制依赖组内多样性，用同一个问题 n 条轨迹的相对 reward 来估计 advantage，8 条轨迹一旦高度趋同，advantage 估计退化成噪声，梯度信号基本消失，训练实际上已经停摆，loss 下降只是格式 loss 还在优化的假象。根因是我们最初 entropy_coeff 设的是 0，完全没有熵正则化，RL 的优化目标只有 reward，没有任何约束鼓励保持输出多样性，模型自然会朝确定性方向收缩。解决方案是加了熵正则项，对输出分布过于尖锐的情况施加惩罚，强制模型在 rollout 时保持一定探索随机性。加了之后 rollout 多样性恢复，组内 advantage 有了区分度，reward 重新开始上升。

第三个是**信用分配。**长轨迹里前几步正确、中间某步工具失败、后面全崩，vanilla GRPO 会把整条轨迹的负 advantage 无差别打到每个 token 上，连失败前的正确推理一起惩罚，模型变得不敢探索——我先试了 hard-masking 发现几乎没提升（69.1 vs vanilla 69.0），因为失败前的 token 仍被负优势惩罚；最后用"失败 step 截断 + 单侧优势截断"解决，只屏蔽失败后缀的噪声、把失败轨迹的负优势归零保护有效前缀，单次改动涨了 2.7 分（69.1→71.8）.

### RL 训练工程上遇到过什么稳定性问题？

最严重的一个是训练过程中偶发性的整体卡死。小规模测试时没出现过，一上大规模并发训练，第二天就开始出问题：训练进程突然停在那里不动，GPU 利用率掉到零，但进程没有退出，也没有报错，就这么一直耗着。

排查下来发现根因是工具调用卡住了。我们的 RL 训练需要模型和外部工具实时交互——模型输出一个工具调用，采样进程真的去执行这个工具，拿到结果再喂回模型。大规模并发下，偶尔有工具的网络请求因为各种原因迟迟没有响应，采样进程就一直等着，不知道对面已经没有反应了。一个进程卡住之后，整批数据里其他进程也要等它，整个训练批次永远跑不完，训练就这样卡死在那里了。

解决方案分三层。

第一层是给每个工具调用加一个明确的等待上限，超时之后直接当作这次工具调用失败处理，不再等下去，失败的工具调用计为一次 失败 step；

第二层是失败后自动重试一次，因为很多网络问题是偶发的，重试一次往往就成功了，避免把一个可以恢复的问题直接变成 失败 step；

第三层是在更高层面加一个独立的进度监控，专门盯着每个采样进程的状态，如果某个进程超过全局时间阈值还没结束，就强制把这条轨迹标记为失败、把进程释放掉，不让它继续拖累整体训练。

### 你们的 SFT 数据（36k条轨迹）是怎么构建的？数据质量是怎么保证的？

数据构建分两个来源：一部分是人工标注的高质量轨迹，另一部分是强模型合成的轨迹。

人工标注部分：从真实客服对话里挑选典型案例，由标注人员将其改写成标准的多轮工具调用格式，每条轨迹平均有2.3次工具调用，覆盖比如比价导购、售后理赔等场景。

合成部分的流程分两步。

第一步是难度过滤，分两个阶段：先去掉模型凭参数记忆就能直接回答的问题，这类问题不需要调工具，保留进 SFT 数据会让模型学到不用工具也行；再去掉单次 image_search 就能解决的单跳问题，只保留真正需要多步推理的。

第二步是轨迹合成与筛选：每道问题让模型跑 K=5 条独立轨迹，在真实工具环境下展开推理，再对这批轨迹做两阶段淘汰。第一阶段按答案正确性过滤，用 LLM judge 判断最终答案是否与标准答案一致；第二阶段按过程质量过滤，评估工具调用的合理性、推理的逻辑一致性、有没有无效重复调用，两阶段都通过的才进入最终数据集。

此外，约 10% 的数据会加入受控的图像降质处理（比如模糊、下采样、透视畸变），并配对对应的增强工具调用轨迹，专门训练模型在图像质量差的情况下主动调用视觉增强工具，而不是直接对原图猜答案。

最终 36k 条覆盖多个场景子类别，这个数量级足够做冷启动。

### RL 阶段的训练数据和 SFT 数据有什么区别？

两者的数据处理流程是一样的：RL 数据来自同一套过滤后的问题池，只是额外采的一份不重叠的 8k 条子集，没有额外的处理步骤。真正的区别在于数据形式：SFT 数据是「问题 + 完整工具调用轨迹」，每条轨迹都告诉模型该怎么一步步调工具、中间推理是什么；RL 数据只有「问题 + 最终答案」，没有任何中间过程，模型需要在训练时自己探索怎样组合工具才能答对。

### 你们怎么验证模型效果，用什么数据评测？

我们自己构建了评测集，共 1000 道题，按业务场景分四个子集各 250 题，每道题都有人工标注的标准答案，用 LLM judge 自动评分，再抽样人工复核。

- 比价导购子集（250题）：用户上传商品图，要求识别品牌型号并给出跨平台比价结论。
- 二手鉴定子集（250题）：上传二手商品的细节图，要求判断真伪并给出鉴定依据。
- 售后理赔子集（250题）：上传商品损坏图或快递面单，要求提取关键信息并给出理赔建议。
- 商品咨询子集（250题）：用户描述商品需求或上传参考图，询问规格参数、兼容性或使用方法。

### 这个项目目前还有哪些可以优化的地方？/bad case列举（必准备）

1. **SFT 数据的难度分布**。事后分析发现，简单轨迹占比偏高，复杂轨迹不足，导致模型在需要多步工具调用的问题上容易过早放弃。未来应该会做更严格的难度均衡采样。
2. **工具能力扩充**。现有 8 个工具覆盖的场景还有明显缺口，比如用户发一张商品外包装图，上面有条形码或二维码，问“这个是不是我订单里的那款”。现在系统可能会先 image_search，再 text_search 商品名，但其实最直接的方式是扫条码定位 SKU。如果没有条码/二维码识别工具，模型只能绕远路，稳定性和效率都会下降。  
   再比如用户发商品开箱视频，展示鞋标、吊牌、瑕疵细节。当前系统主要处理静态图片，只能让用户再截图上传，或者从视频里取不到稳定证据。这类 case 在售后、鉴定场景里很常见。  
   还有历史价格查询。现在如果用户问“现在买划不划算，是不是历史低价”，模型可能用 text_search 拼关键词查价格信息，但这不如单独封装一个历史价格接口稳定。后续比较值得扩展的工具包括条码/二维码识别、视频关键帧提取、历史价格查询等。
3. **视觉工具调用没有足够细粒度奖励。**比如用户上传的快递面单很歪，模型应该先调用 perspective_correct，再 OCR 提取物流单号。但有时模型会直接 OCR，导致识别错单号，后面物流查询也跟着错。  
   再比如商品细节图很糊，模型应该先 super_resolution 或 sharpen，再做鉴定细节比对。但如果最终答案错了，RL 只能通过终态奖励倒推，很难明确告诉模型“你错在没有先做图像增强”。  
   现在的 r_query 主要对文字检索质量打分，比如查询词是否精准、检索是否递进；但 crop、透视矫正、超分辨率这些视觉工具调用，缺少专门的过程奖励。模型什么时候该调用视觉工具、调用得好不好，在训练时反馈不够细。  
   后续优化方向是训练一个覆盖视觉工具调用的 process reward model。它不仅判断最终答案对不对，还要判断视觉处理动作是否合理，比如是否裁到了关键区域、是否应该先增强再 OCR、是否避免了无效图搜。
4. **奖励模型不稳定**。现在用 GPT 做 judge，成本高、版本不固定，一旦 API 行为有变化就会引入训练噪声。更稳定的做法是用开源模型训练一个专门的过程奖励模型，既能降低依赖，也能把 judge的评估范围扩展到视觉动作上。

### 模型训练完之后是怎么部署上线的？

首先是**整体架构**。线上系统分三层：模型推理服务、工具服务、Agent 推理循环。SFT+RL 训练完的最终模型单独部署为推理服务；23 个工具各自部署为独立微服务，视觉处理工具本地化部署控制延迟，检索工具挂载对应的向量库和知识库，业务操作工具（比价、退款跟踪、防伪验证等）直连后台业务系统；Agent 推理循环作为中间层，把模型和工具服务串联起来驱动整条推理链路。

其次是**推理引擎优化**。模型推理层用 vLLM 部署，核心是 PagedAttention 机制：通过分块管理 KV cache 减少显存碎片，支持高并发请求的连续批处理，能自动处理不同长度的输入序列。多模态输入（图像 + 文本）先把图像 token 化再送入模型，图像分辨率统一限制在 262,144 像素以内控制 token 数。

第三是 **Agent 推理循环的工程设计**。每条请求进来后走多轮循环：模型输出 thought 和工具调用指令 → 解析器提取工具名和参数 → 执行工具拿到结果 → 结果拼回 context 给模型 → 判断继续调工具还是生成最终答案，最多 10 轮。为控制响应时间上界，做了两个提前终止机制：连续 3 次失败 step（工具调用失败或超时）直接终止；输出内容 n-gram distinct ratio 低于 0.5 且词数超过 2500 判定为重复生成并截断。工具调用层设有超时阈值，超时后标记为失败step 并自动重试一次，防止慢工具拖死整条链路。

最后是**服务性能指标**。端到端时延是用户侧感知的完整请求耗时，每轮循环都要经过工具执行，平均 2-3 次工具调用的请求 P50 在 6 秒左右、P95 在 12 秒以内，MAX_TURNS=10 的 hard cap 保证最长响应时间可控。QPS 方面，TP=8 单实例压测峰值约 20 QPS，工具调用等待窗口期让 GPU 有余量处理其他请求，通过多实例横向扩展覆盖业务峰值。

### Bad case 回流怎么做的

1. 线上推理会采集bad case，比如模型工具调用逻辑出错（不做图像增强直接检索、重复调用同一工具、工具失败后不会换路径等），最终答案错误（比价价格不对、鉴定真伪结论出错、售后理赔建议不符合平台规则等），以及要求转人工的用户会话都会落库，记录完整上下文：包括用户图文输入、模型每一轮thought、tool call、工具返回observation、最终输出、对应23个工具的执行日志、失败step标记等。
2. 过滤清洗，过滤网络超时、工具接口临时故障这类非模型策略问题，只保留模型推理决策缺陷导致的样本，再人工抽样复核，剔除标注歧义、用户输入信息缺失无法作答的无效case，剩下的有效bad case进入回流池。
3. 分两条回流链路，一条回流SFT数据集，一条用于扩充RL训练问题池。
- 回流SFT：针对每条bad case人工修正完整多轮工具轨迹，补齐正确的thought和工具调用顺序，比如原图模糊漏超分的样本，补充先super_resolution再image_search的标准链路；中间工具返回无效结果不会切换检索词的样本，新增重试、更换检索关键词的分支；同时按照数据构建规范，10%左右样本加入受控图像降质构造难例轨迹，之后对修正后的轨迹做两轮筛选，先用LLM judge校验答案正确性，再评估工具调用过程逻辑是否合理，合格的样本追加进原有36k SFT数据集，用于下一轮SFT迭代，让模型提前见过这类错误场景的标准解法。
- 回流RL：只提取bad case里的用户原始问题和人工标注标准答案，不提供中间修正后的工具轨迹，追加到8k高难度RL问题池，RL训练时模型需要自己在工具环境里rollout多条轨迹探索正确路径，对于比较突出的bad case范式也可以设计奖励进行惩罚，靠奖励约束避开之前的错误决策，相当于用真实线上缺陷样本强化模型自主纠错能力。
1. 回流后的闭环验证，每轮SFT和RL迭代完成后，在1000题自建评测集单独拆分bad case子集做专项评测，对比修正前后准确率、工具调用失败率、重复调用占比，同时把高频同类bad case提炼成系统提示词约束，提前限制模型容易出错的调用逻辑，减少同类问题复现。

#### 29.1 如何拒绝采样挖掘有价值的RL数据进行训练（可以拓展到别的项目）

1. 先定义什么是有价值的样本。比如分为三类：一是边界样本，同一个问题多次 rollout 有对有错、成功率处于中间地带，说明模型还没完全掌握，学习增益最大，采样时用当前策略对高难度问题池做多轮 rollout，每个 prompt 采样 8 条，和 GRPO 的 group 采样复用同一套流程，并配合不同温度或不同基座模型增加轨迹多样性，避免同源采样出来的轨迹高度趋同；二是失败可纠正样本，过程前缀合理但最终失败的轨迹，配合失败 step 截断和单侧优势截断训练纠错能力；三是答对且过程高效的轨迹，作为正向信号强化稳定路径。。
2. 然后做过滤：先做难度过滤，去掉模型稳定答对、一次就过的简单问题；再做过程质量过滤，筛掉重复调用、过早放弃、死循环包含很多噪声的轨迹对应的数据；最后做多样性去重，按工具调用序列相似度合并高度雷同的轨迹对应的问题，保证留下来的样本覆盖不同工具链。
3. 整个筛选标准是在迭代的，每轮 RL 后/新模型上线后，需要用新模型重新采样，根据 reward 分布/线上指标调整过滤策略，并和线上 bad case 回流链路打通，形成"采样-筛选-训练-再采样"的迭代闭环。

### 为什么要训练自己的模型，对比 通用模型 + harness的优劣

1. 自己训练的模型成本更低延迟更低，隐私性更好，并且因为有很多自己的工具，直接调用通用模型的skills召回准确率和skills遵循性都不如自己训练后的模型，对比结果可以说自己的训练模型比通用模型高几个点。
2. 通用模型有通用工具调用能力，但这个能力是预训练里学的泛化能力，没有针对电商客服这个具体场景优化，换句话说没法保证他召回的skills是准确的，以及他能否充分理解skills中的业务逻辑，遵循skills进行输出。通过训练让他接触一些实际数据，什么信号组合调用哪个skills，调用skills结果不理想怎么办，大模型面对skills呈现是不同结果怎么办...这都能增强模型回复的准确性。
3. harness方案的本质是把策略写死在prompt和工作流里，比如规定"分辨率小于xx，先图像增强再识别再检索"，模型按harness要求工作。但真实场景里的决策是harness写不完的：中间工具返回低质量结果时是重试还是换工具，多个检索结果冲突时信哪个，证据不足时是继续搜还是直接让用户补图等等。harness写的多了可能不同harness之间就会存在冲突，维护这些harness的成本也会增加。而通过训练的方式，SFT给了示范轨迹让模型学习，RL让模型在真实工具环境里自己探索，让模型把复杂的业务逻辑进行内化，后期有新的场景，工具直接构造新的数据就行。
4. harness的优点在于开发成本低，遇到问题改改prompt，增加个节点可能就解决了。但是harness+模型的上限就取决于harness ，模型对于你的业务场景，skills不了解，执行成啥样全靠harness质量，但不可避免的是随着业务越来越复杂，这些harness规则写的越来越多，整个链路都会变得更加复杂。

### 有过程奖励惩罚冗余工具调用吗，为何还要做截断。有些连续多次工具调用失败很可能是由于前面的内容导致的，你删掉了模型如何学会避免这种错误

1. 过程奖励和截断解决是互补的， 过程奖励 r_query 的粒度是整个轨迹，通过梯度引导模型少做，一个结果和格式都正确、过程中出现了比较多失败的轨迹，也可能拿到中等奖励从而被激励，也就是中间的不好的token可能还会污染梯度。选择3次失败以后进行截断，就是排除掉了包含过多中间过程失败的步骤，避免这些中间失败被当成正向信号被鼓励。
2. 失败 step 只截断失败点之后的 token，而导致失败的关键决策（比如连续调用中前两次就选错了工具、参数不对等等）和前3次调用失败发生在失败点之前，那些 token 依然参与训练，这个轨迹的前半部分还是参与训练，但是因为他被截断了，他的结果奖励肯定是0，不合理的调用也会被过程奖励 r_query 打低分，整体奖励值也会比较小，这个轨迹前边导致失败的部分也会被抑制。

### vllm

#### PagedAttention

PagedAttention通过将KV（Key-Value）缓存划分为固定大小的块（类似于虚拟内存中的页），实现了对内存的高效管理。这种设计允许系统根据实际需求动态分配和管理显存，从而提高了推理速度和资源利用率。

优化策略

- **连续批处理**：利用连续批次操作完成多个序列的推理，提高了GPU的利用率。
- **调度与抢占**：采用先来先服务的vllm是先进的大语言模型推理框架调度策略，并在需要时抢占资源，以处理更多的请求。
- **分布式管理**：优化了通信机制，提高了系统的扩展性和性能。

#### **PagedAttention的优点**

1. **页按需分配：**PagedAttention 将每个请求的 KV Cache 拆分为若干固定大小的页，并仅在生成新 tokens 时按需分配物理页，无需提前为最大序列长度预留内存，从而大幅降低 KV Cache 内存占用。
2. **跨请求 KV Cache 共享：**相同前缀的多个请求可共用 KV pages，大幅降低内存占用，适用于beam search、A/B test等场景。
3. **消除zero-padding：**传统方法往往需将所有序列填充到同一最大长度，导致短序列浪费大量内存和计算。PagedAttention 只在实际需要的 blocks 上分配内存，短序列不会因对齐而被额外填充，从而**zero-padding**问题被根本杜绝。
4. **提升推理吞吐：**由于减少了内存浪费和碎片，GPU 可以在同等显存下加载更多并发请求，vLLM 的实测表明 PagedAttention 能带来 2–4× 的整体吞吐提升，且在中长序列下优势更明显。

### 分布式训练

#### PP

- **做法：** 将模型的不同层（Layer）按顺序分布到不同的显卡上。例如，一个 24 层的模型，1-12 层放在 GPU 0，13-24 层放在 GPU 1。数据像流水线一样，先在 GPU 0 计算，结果传给 GPU 1 继续算。
- **特点：** 解决了单卡装不下模型的问题，通信量相对较小（只在层与层之间交换激活值）。
- **局限：** 存在“流水线气泡”问题，即后方的显卡在等待前方显卡计算结果时会处于闲置状态，计算效率受影响。

#### TP

- **做法：** 将每一层内部的权重矩阵切开，分到不同的显卡上。计算时，多张显卡协同完成同一个矩阵乘法。
- **特点：** 颗粒度最细，能处理单层参数就极大的超大模型。
- **局限：** 通信频率极高，每计算一层都要在显卡间同步数据。通常要求显卡之间有极高的带宽（如 NVLink），一般只在同一个机器内部的显卡间进行。

#### CP

上下文并行是一种针对超长序列训练的分布式策略。它将输入文本的序列维度拆分到多个 GPU 上，每个 GPU 只处理序列的一部分，从而突破单卡显存对文本长度的限制。CP 的核心在于处理 Attention 计算。在计算过程中，每个 GPU 持有自己的一段 Query ，但为了计算完整的注意力，它需要看到全量文本的 Key和 Value 。

为了实现这一点，CP 采用了环形通信机制：

- 所有的 GPU 排成一个环。
- 每个 GPU 在本地计算自己的 Query 与当前持有的 Key/Value 的结果。
- 计算的同时，GPU 将手里的 Key/Value 传递给环里的下一个 GPU，并接收上一个 GPU 传来的新数据。
- 经过一轮循环，每个 GPU 都用自己的 Query 遍历了所有的 Key/Value，从而完成了全局注意力的计算。

解决了以下问题：

- 显存溢出：序列长度增加时，注意力矩阵的显存占用呈平方级增长。CP 将这个巨大的矩阵分散到了多张显卡上。
- 算子瓶颈：传统的序列并行（SP）在进入注意力计算前往往需要汇聚成完整序列，这在处理几十万长度的文本时会导致单卡显存直接炸掉。CP 则让单卡始终不需要看到完整序列。

### Qwen3.5 介绍

Qwen3.5 是一个支持多模态输入的 Causal LM with Vision Encoder 模型。它公开了 **Qwen-3.5 Dense** 和 **Qwen-3.5-MOE** 两类模型：Dense 版本使用 Qwen3-Next 的混合注意力主干，并接入 ViT 和 PatchMerger；MoE 版本则在 Dense 主干基础上，将 LLM 中的 FFN 替换为 MoE 架构，从而在保持较低激活参数量的同时扩大模型容量。

- **文本基座：继承 Qwen3-Next 的混合架构**

Qwen3.5 的文本主干来自 Qwen3-Next。核心设计是 **Hybrid Attention**：在若干层线性注意力中周期性插入标准注意力层。

1. **线性注意力负责效率**：Gated DeltaNet 打破标准注意力的二次复杂度，在长文本场景下显著降低计算和显存压力。
2. **标准注意力负责召回和推理**：Gated Attention 保留完整注意力建模能力，补足线性注意力在精确检索、复杂依赖和深层推理上的短板。
3. **循环块结构清晰**：LLM 模块共 60 层，由 15 个循环块组成，每个循环块包含 **3 个 Gated DeltaNet + 1 个 Gated Attention**。
- **Gated DeltaNet：面向长文本的高效线性注意力**

Gated DeltaNet 是 Qwen3.5 中承担高效上下文处理的核心模块。它包含 **64 个用于 V 的线性注意力头**，以及 **16 个用于 QK 的头**，注意力头维度为 128。

这个设计适合大词表和长上下文场景：一方面能快速抽取局部和长程特征，另一方面能降低长序列推理时的计算成本。文档中还提到，Qwen3.5 的 Embedding 维度达到 **248,320**，因此高效特征提取对整体吞吐非常关键。

- **Gated Attention：保留标准注意力的表达能力**

Qwen3.5 的标准注意力层采用 Gated Attention，并使用 GQA 结构：**2 个 Q 头、2 个 KV 头**，注意力头维度为 256，RoPE 嵌入维度为 64。

Gated Attention 的关键是在标准 Scaled Dot-Product Attention 输出后加入一个依赖输入的门控：

1. **增强非线性表达**：门控机制在注意力输出和后续线性投影之间加入非线性变换，缓解标准注意力低秩表达的问题。
2. **动态抑制噪声**：Sigmoid 门控可以让部分输出趋近于 0，使模型根据当前 Query 抑制无关信息。
3. **缓解 Attention Sink**：传统模型中 BOS 等早期 token 容易吸收大量注意力，Gated Attention 允许模型过滤这些无效注意力。文档中提到，引入门控后，沉没注意力比例可从 46.7% 降至 4.8%。
- **多模态架构：ViT + PatchMerger + LLM**

Qwen3.5 去掉了 Qwen3-VL 中的 DeepStack 架构，回到更传统、更简洁的 **ViT + PatchMerger + LLM** 路线。

1. **ViT 负责图像编码**：将图像切成 patch，并提取视觉特征。
2. **PatchMerger 负责视觉 token 压缩**：减少视觉 token 数量，降低进入 LLM 的上下文压力。
3. **LLM 负责统一理解与生成**：把文本 token 和视觉 token 放到同一个生成式模型中建模，从而支持图文理解、视觉问答、多模态推理等任务。
- **MoE 版本：397B 总参数，17B 激活参数**

Qwen3.5-MOE 在 Dense 主干基础上引入 MoE。文档中给出的配置是：总共 **512 个路由专家**，每次推理激活 **10 个路由专家 + 1 个共享专家**，专家中间维度为 1024。

整体规模上，Qwen3.5-MOE 的总参数量达到 **397B**，但实际激活参数量只有 **17B**。这类设计的优势是模型容量很大，可以存储更多知识和任务模式；单次推理只激活少量专家，计算成本接近中等规模模型。

- **长上下文能力：原生 256K，可扩展到 1M**

Qwen3-Next 原生支持 **256K 上下文窗口**，并可以通过 YARN 进一步扩展到 **1M**。Qwen3.5 继承这一长文本能力后，更适合长文档理解、代码仓库分析、多轮对话记忆、Agent 轨迹分析等场景。

线性注意力负责降低长上下文成本，标准注意力负责保留关键位置的精确建模能力，这也是它采用混合注意力架构的核心原因。

**推理效率：MTP 提升生成速度**

Qwen3.5 还引入了 MTP 机制，即一次推理生成多个 token，用于提升投机采样效率。它的目标是降低自回归生成中“一次只预测一个 token”的延迟瓶颈，让长回答、代码生成、多轮推理任务的吞吐更高。

### 强化学习相关

#### 强化学习与SFT的区别

- **优化目标**：SFT和强化学习的优化目标相似，即都是在优化某个数据分布下的一个分数值的期望。
- **优化方法**：二者优化的途径是不同的，SFT直接通过优化模型对于数据特征的输出来优化目标，数据分布不变；**强化学习可以通过改变策略来调整智能体和环境交互数据的分布，进而优化目标。**
- **训练目标**：SFT关注寻找一个模型，使其在给定数据分布下得到的损失函数的期望最小；强化学习关注寻找一个智能体策略，使其在与动态环境交互的过程中产生最优的数据分布，即最大化该分布下一个给定奖励函数的期望。
- **训练周期**：SFT的数据是静态的，只用在给定数据集上训练进行一次性训练。强化学习的数据可以不断产生，可以持续训练，通过不断地与环境交互更新策略。
- **数据**：SFT需要标注数据集，强化学习不依赖标注数据集，而是通过与环境交互产生数据。
- **损失函数**：SFT的损失是准确的，可以直接根据标签和预测计算损失。强化学习只能从环境或奖励模型获取奖励，从环境获取奖励一般是延迟的，奖励模型给出的奖励不一定准确，计算得到的损失不一定准确。

#### GSPO对GRPO做了什么改进

- GRPO在token级别计算重要性权重，以修正新策略和旧策略之间的偏移，但这单个token对重要性可能波动很大，带来了高方差的训练噪声。这种噪声随着响应长度的增加而逐步累积，即随着链式乘积在序列层面不断增大。
- 并且被clip机制进一步放大，clip可能对有效梯度强行截断，破坏梯度方向一致性，等于在已高方差的权重上再做非线性“压扁/截断”。
- 这很容易导致模型崩溃，特别是MoE模型，因为在经过一轮或多轮梯度更新后，相同查询激活的专家可能会变化，导致$w_{i,t}(θ)$产生剧烈震荡。

GSPO的提出是为了解决 GRPO 在长序列和 MoE 模型训练中容易失稳的问题。GSPO 将优化粒度从 **token 级** 提升到 **序列级**，基于序列似然来定义重要性比率，并在序列层面执行奖励与优化。这样一来，训练信号更加一致，显著提升了训练的稳定性与效率，尤其在大规模 MoE 架构中优势突出。

#### 用通俗的语言解释GSPO的原理

想象你在教一个学生写作文：

- **GRPO的做法**：我会逐字逐句地给每个词打分，这个词好给高分，那个词差给低分
- **问题**：不同词的分数差别很大，有些词被大幅鼓励，有些词几乎没反馈，训练过程就像坐过山车一样不稳定
- **更严重的是**：在MoE模型中，同一个问题在不同训练阶段可能激活不同的"专家模块"，就像你今天用左手写字，明天突然换右手，这种不一致性会让模型彻底崩溃

**GSPO核心理念**：既然奖励是针对整篇文章的，那训练也应该针对整篇文章进行

**GSPO的做法**：

1. **整体评分**：不再逐词打分，而是给整个回答一个总体评价
2. **统一对待**：如果这个回答好，那么其中每个词都同等程度地被鼓励；如果回答差，每个词都同等程度地被惩罚
3. **长度归一化**：无论回答是10个字还是100个字，都用统一的标准来评判

#### 奖励劫持

**奖励劫持**（Reward Hacking）是指在强化学习中，智能体利用奖励函数中的缺陷或模糊性来获取高奖励，而没有真正学习或完成预期的任务。奖励劫持的存在是因为强化学习环境通常是不完善的，并且准确地指定奖励函数从根本上具有挑战性。比如你想让机器人打扫房间，你得奖励设置为地面上垃圾越少，奖励越高，但是机器人发现，把所有垃圾都扫到地毯底下，或者用个大东西把垃圾盖住，传感器就检测不到垃圾了，于是能拿到超高分！但房间实际上还是脏的。

奖励劫持的产生主要有以下原因：

- **奖励函数设计缺陷**：奖励函数可能没有准确地反映设计者的意图，或者没有考虑到所有可能的情况，导致智能体可以找到捷径来获取高奖励。
- **环境复杂性**：强化学习环境可能非常复杂，智能体可能会发现一些设计者未预料到的行为来最大化奖励。
- **部分可观察状态**：智能体可能无法完全观察到环境的状态，从而导致其行为与设计者的预期不一致。

#### 怎么缓解奖励劫持

1. 设计更智能、全面的奖励函数

- **多维度考量**：不要只盯着单一指标。例如，在打扫机器人场景下，除了统计“垃圾清理量”，还应对“将垃圾准确投掷进垃圾桶”这一关键动作进行奖励；
- **目标对齐**：奖励函数要尽量反映最终业务或任务目标，而非表面现象。这个过程需要不断试验与打磨；
- **引入惩罚项**：对一些明显偏离目标的行为（如机器人将垃圾藏匿）设置扣分或负奖励，增加防范强度。

2. 强化人工监督与定期审查

- **超越分数盲信**：奖励分数高并不意味着策略无懈可击，要定期检查 AI 实际执行的行为；
- **及时干预**：一旦发现模型开始钻空子，应迅速调整奖励函数，或通过人类反馈明确告知“不允许这样做”，类似 RLHF 中的人工反馈环节。

3. 多目标奖励与硬性约束

- **多信号协同**：在复杂任务中，单一奖励往往不够，可并行设置若干子目标，让模型在各个维度上都达到预期；
- **硬性规则**：对一些绝对不容违背的原则（如“禁止将垃圾扫入地毯下”）直接设为不可逾越的约束，而非靠奖励惩罚试图引导。

4. 正则化与行为规范性惩罚

- **KL 散度惩罚**：在 PPO 或其他策略优化中，常添加与原始“良好行为”模型（如 SFT 模型）之间的 KL 散度惩罚，以防新策略过度偏离、产生怪异行为；
- **限制偏移**：这样既能追求更高回报，又能控制模型行动风格，避免“剑走偏锋”。

5. 对抗性测试

- **模拟攻击者思维**：主动思考 AI 可能的取巧路径，设计专门的测试场景进行“红队”式攻击；
- **持续迭代**：针对发现的漏洞不断修补奖励函数或约束机制，提高系统鲁棒性。

6. 基于人类偏好的学习（RLHF）

- **学习偏好胜过完美奖励**：RLHF 不要求你精确定义所有奖励规则，而是通过人类偏好示例来训练奖励模型；
- **更接近直觉**：人类可以一眼分辨真正有价值的结果与“耍小聪明”的结果，这使得训练出的奖励信号更加健壮、贴近业务目标。

7. 简化原则

- **保持精简**：过于复杂的奖励机制更容易被模型钻漏洞；
- **直接明了**：在条件允许的情况下，尽量将目标与奖励设计得简洁、易于理解和验证。

#### 怎么解决熵坍塌

1. **熵正则化损失：** 在PPO损失中加入策略熵正则项，鼓励模型保持探索性，避免过早收敛到确定性最优路径。
2. **清洗低质量、矛盾、噪声标注数据：**避免训练数据中存在n-gram大量重复等问题，带歪模型。
3. **奖励函数正则：**重构奖励设计，提供更丰富的奖励信号，避免模型单调化。
4. **采样与推理策略：**训练+推理阶段启用Top-p 采样、调高温度系数，平滑输出分布，缓解推理阶段熵坍缩。

## **一、先一句话理解 DDD 是什么**

**DDD = 用“业务语言”来设计系统，而不是用“技术对象”硬套业务。**

- 不是 <u>表怎么建、接口怎么拆</u>
- 而是**业务里到底有哪些“概念”、这些概念如何协作、规则放哪**

---

## **二、没有 DDD 的常见写法**

以**下单系统**为例。

### **典型 CRUD 写法**

```
OrderService {
    createOrder()
    payOrder()
    cancelOrder()
}
```

```
order(id, user_id, status, price, create_time)
```

代码里会出现：

```
if (status == 1) { // 已创建
    // ...
}
if (status == 2) { // 已支付
    // ...
}
```

**问题在哪？**

1. 业务规则散落在 Service、Controller、SQL 中
2. 改一个规则（比如“支付后不能取消”），你要全局搜

也就说说：**<u>系统是“技术驱动”的，不是“业务驱动”的</u>**

---

## **三、用 DDD 的方式重写这个例子**

### **先不写代码，先问一个问题**

在“下单”这个业务里，**最核心的东西是什么？**

答案是 **订单**

这在 DDD 里叫：**领域对象**

---

### **用“业务语言”定义 Order**

```
class Order {
    OrderId id;
    OrderStatus status;
    Money totalPrice;

    void pay() {
        if (!status.canPay()) {
            throw new IllegalStateException("当前订单不能支付");
        }
        status = OrderStatus.PAID;
    }

    void cancel() {
        if (!status.canCancel()) {
            throw new IllegalStateException("当前订单不能取消");
        }
        status = OrderStatus.CANCELED;
    }
}
```

```
enum OrderStatus {
    CREATED,
    PAID,
    CANCELED;

    boolean canPay() {
        return this == CREATED;
    }

    boolean canCancel() {
        return this == CREATED;
    }
}
```

**注意变化点：**

- 业务规则 **不在 Service 里**
- 状态变化 **由 Order 自己负责**

---

### **Service 只负责“协调”，不负责规则**

```
class OrderApplicationService {

    void pay(OrderId orderId) {
        Order order = orderRepository.find(orderId);
        order.pay();
        orderRepository.save(order);
    }
}
```

Service 变得很“薄”，几乎不写 if-else

---

## **四、这就是 DDD 的核心思想**

**用一句工程化的话说：**

**业务规则应该待在“最懂业务的对象”里，而不是散落在各层代码中**

---

## **五、DDD 给你带来的真实好处**

### **代码可读性暴涨**

```
order.pay();
order.cancel();
```

而不是：

```
if (order.getStatus() == 2 && flag == 1) { ... }
```

### **业务变更成本显著降低**

比如新增规则：

「支付 30 分钟后才能发货」

你只改：

```
order.canShip()
```

而不是改 多 个 Service + 多个 SQL

---

### **面向复杂业务特别有优势**

DDD 适合的不是“用户表 + 增删改查”，而是业务非常复杂的时候，比如业务包含：

- 订单
- 账户
- 结算
- 风控
- 计费
- 工作流

**<u>规则越复杂，DDD 收益越高</u>**

---

### **天然适合微服务拆分**

领域边界清晰后：

- 订单域
- 支付域
- 库存域

**<u>拆服务不是拍脑袋，而是“领域边界”驱动</u>**

**一句话总结**

**DDD 不是一种技术，而是一种“以业务为中心”的建模思想**

它通过领域模型，把复杂业务规则收敛在正确的地方，让系统更稳定、可演进。
